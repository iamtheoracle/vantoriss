# Project Black — Identity and Financial Control Review

**Scope:** Read-only review of `iamtheoracle/vantoriss` on `project-black/unified-inventory` against `iamtheoracle/vantoris-credit-union`.  
**Status:** Findings documented; application code has not been changed by this review.

## Executive summary

The two frontends point at the same Base44 application ID (`6a3d85c1632966fefe16f3d4`) and server (`https://vantoris.base44.app`). They are therefore not demonstrably independent account systems: they appear configured to share the same Base44 backend. Confirm the live Base44 app and deployment ownership before consolidating deployments.

The neutral `vantoriss` repository remains the provisional umbrella shell, but it must not be treated as production-ready for financial activity. The highest-priority issues are identity semantics, server-side authorization, and non-atomic balance posting.

## 1. Identity and sign-in findings

### Current behavior observed

- `src/pages/Login.jsx` in `vantoriss` labels the identifier **User ID**, but uses an HTML `type="email"` field and calls `base44.auth.loginViaEmailPassword(userId, password)`. The UI therefore presents a User ID contract while the code submits the value as an email credential.
- `src/pages/Register.jsx` registers using `{ email, password }`, then writes `username: data.userId` through `base44.auth.updateMe` after OTP verification.
- Registration derives a default username from the part of the email before `@`. That value may collide with another user's chosen username and must not be treated as a unique identifier without server-side enforcement.
- The entity schema describes `username` as a unique chosen username, but the schema shown does not itself demonstrate a uniqueness constraint.
- The login implementation in `vantoris-credit-union` is also email/password-based; it attempts to persist the returned session token and selects the operations landing page after checking the authenticated user's role. `vantoriss` currently navigates all successful logins to the member home, leaving the existing route guard to control operations access.

### Required identity model

Keep these identifiers separate in UI, data and authorization:

1. **Immutable internal user ID** — generated by the identity system; primary relationship key; never user-editable.
2. **Login credential** — email/password and supported identity-provider sign-in (such as Google). A Google sign-in must still resolve to the same internal user record and must not create an accidental duplicate identity.
3. **Public username / handle** — user-chosen, human-readable, unique under a defined normalization rule; for display, search and social discovery. It is not the internal ID or a financial account number.
4. **Financial account number** — separately generated, non-editable identifier scoped to an account and never used as the platform's primary user identity.
5. **Business / organization identity** — distinct from a person's user identity and governed by membership and role assignments.

If the product requires a bank-style numeric User ID, issue it server-side as a separate public login identifier only if the identity provider supports a secure server-validated lookup flow. Do not simply pass a numeric ID to an email/password endpoint. Never look up a user's email in browser code and then authenticate without server-side controls, rate limiting, enumeration protection and audit logging.

### Safe implementation sequence

- First document the supported sign-in contract with the identity provider: email/password, Google OAuth, and whether numeric IDs are supported natively or require a server-side authentication broker.
- Update labels and input types to match the actual supported login contract. Do not advertise username or numeric-ID login until it is implemented and tested end-to-end.
- Enforce normalized username uniqueness on the authoritative backend; reserve immutable user IDs and financial account numbers for separate purposes.
- Ensure role and workspace access come from trusted server-side claims/permissions, never from the identifier entered or a client-selected destination.
- Test duplicate emails, duplicate usernames, case/Unicode normalization, OAuth account linking, expired sessions, disabled accounts, role changes, and attempts to access operator routes as a normal member.

## 2. Financial control findings

### Approval flow

In `vantoris-credit-union/src/pages/operations/Approvals.jsx`, approval reads an account balance in the browser, calculates a new balance, updates `Account.balance`, and then separately updates the transaction status. This permits concurrent approval races and partial completion if one update succeeds and the other fails. The browser must not be the authoritative financial posting engine.

### Bulk import

In `base44/functions/bulkImportTransactions/entry.ts`, each imported transaction is created and the account balance is updated in separate calls. The current flow does not demonstrate a durable idempotency key, replay protection, atomic posting, or a review-before-post batch state. A failure between writes can leave the transaction and balance inconsistent; retrying can duplicate a posting.

### Export

In `base44/functions/exportTransactionLedger/entry.ts`, exported rows hardcode transaction `Status` to `completed` and `Approval Status` to `approved`. The export must reflect actual source status and approval state, including pending, declined, failed and reversed cases. Do not infer approval from the fact that a transaction exists.

### Data model

The current `Account` schema exposes a mutable numeric `balance`; the `Transaction` schema has a numeric `amount` and `balance_after`, but the inspected schemas do not show a double-entry journal-line model or an explicit currency field. This is not enough evidence of an auditable multi-currency ledger.

### Required target

- Route all balance-changing operations through an authenticated, server-authoritative posting command.
- Use an ACID-capable transactional datastore for atomic journal writes and balance projection updates; do not simulate atomicity with sequential browser or entity API calls.
- Store monetary values as integer minor units or validated decimal types, with explicit ISO currency per account and journal entry.
- Enforce idempotency and unique transaction references at the server/data layer.
- Model immutable journal entries and balanced debit/credit lines; corrections should be reversals plus replacement entries, not silent edits.
- Separate request, approval, external payment execution, settlement, and reconciliation states.
- Require independent permission checks, approval limits, dual control for sensitive operations, audit events, and reconciliation.
- Make imports previewable, deduplicated, resumable and reconcilable before they affect balances.
- Export source-of-truth statuses and preserve a reproducible export manifest.

**Important platform constraint:** if the current Base44 data API cannot provide the required atomic transactions and uniqueness guarantees, the safe fix is to introduce an ACID-capable ledger service/database. A sequence of Base44 entity writes must not be described as a production ledger.

## 3. Repository / deployment finding

Both repositories' inspected `app-params.js` files default to the same Base44 app ID and server URL, and both `base44Client.js` files instantiate the SDK from those parameters. This suggests a shared backend configuration. Verify the actual Base44 app, Netlify site IDs, environment variables, functions and deployment history before choosing a single deployment or removing either repository.

## 4. Priority order

1. **P0 — prevent unsafe financial posting:** disable or clearly mark simulated money movement until all balance changes go through an atomic, server-authoritative ledger path.
2. **P0 — align identity contract:** do not label an email-only endpoint as generic User ID login; define whether numeric IDs are supported before implementing that experience.
3. **P1 — backend identity guarantees:** enforce unique usernames, immutable internal IDs, safe OAuth account linking, and server-side role/workspace authorization.
4. **P1 — correct export and import semantics:** source real statuses; implement idempotent import batches and reconciliation.
5. **P2 — consolidate repositories deliberately:** compare and port features by reviewed file groups; verify Base44/Netlify ownership and configuration first.
6. **P2 — run verification:** install dependencies and run build, lint, typecheck, and tests in a reproducible environment; record actual results rather than assuming they pass.

## Review boundary

This is a static source review. No authentication flow was executed, no deployment was changed, no financial transaction was posted, and no build/test result is claimed. The findings should be revalidated against the active backend and deployment configuration before production changes.
